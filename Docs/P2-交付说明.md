## 1. 现在能干什么

叙述者不再只会"挑一个原版事件"。它现在可以：

1. 判断「这个原版事件表达不了我想讲的东西」→ 选择 `lua_event`；
2. **第二次调用**模型，让它现场写一段 Lua 脚本；
3. C# 侧编译 → 校验 → 执行首阶段 → 落地动作（信件、选项、生成物品/角色、触发原版事件）；
4. 玩家做出选择后 → 信号回到脚本 → 进入下一阶段 → 直到 `done`；
5. 全过程可存读档、幂等、有预算上限。

## 2. Lua 契约（AI 必须照这个写）

```lua
function run(ctx, state)
  local actions = {}
  local s = state

  if ctx.trigger == "start" then
    actions[#actions+1] = { opId = "a1", type = "story.send_letter",
      args = { title = "山谷里的光", text = "夜里，西侧山谷浮起淡蓝色的光。" } }
    actions[#actions+1] = { opId = "a2", type = "story.show_choices",
      args = { prompt = "要派人去看看吗？", options = {
        { id = "go", label = "带人前往" }, { id = "stay", label = "按兵不动" } } } }
    s.stage = "await_choice"
    return rim.aist.json_encode({ actions = actions, next_state = s,
      stage = "await_choice", timer = { hours = 2, signal = "game_timer_due" } })

  elseif ctx.trigger == "choice_selected" then
    if ctx.payload.choice == "go" then
      actions[#actions+1] = { opId = "a3", type = "incident.fire",
        args = { defName = "RaidEnemy", points_multiplier = 0.8 } }
    end
    s.stage = "done"
    return rim.aist.json_encode({ actions = actions, next_state = s, done = true })
  end

  return rim.aist.json_encode({ actions = actions, next_state = s })
end
```

**ctx 字段**：`trigger`（`start` / `game_timer_due` / `choice_selected`）、`payload`（含 `choice`）、`instance_id`、`event_title`、`day`、`tension`、`colonists`、`stage`。

**沙箱**沿用 RimLua 的硬沙箱。事件专用的 `rim` 表提供 `rim.aist.json_encode` 和 `rim.aist.version`，游戏对象和其他模组注册的接口均不可用。

**返回契约**：`rim.aist.json_encode({ actions=..., next_state=..., done=..., timer=..., stage=... })`。
`timer` 支持 `{hours=n}` / `{days=n}` / `{ticks=n}`，默认信号 `game_timer_due`。
`timers` 可传多个定时器。到期时按时间顺序触发，推进阶段后其余定时器继续等待，事件结束或失败时全部清除。

## 3. 动作表（白名单，C# 硬编码权限与范围）

| type | 参数 | 限制 | 校验失败后果 |
|---|---|---|---|
| `story.send_letter` | `title`≤80、`text`≤1200 | 二选一不能全空 | 整阶段作废 |
| `story.show_choices` | `prompt`≤600、`options` 2–4 个 `{id,label≤40}` | — | 整阶段作废 |
| `story.remember` | `text`≤400 | — | 整阶段作废 |
| `incident.fire` | `defName`、`points_multiplier` | 必须在候选表内、`CanFireNow` 为真、配额允许、倍率 ∈[0.3,2.0] | 整阶段作废 |
| `thing.spawn` | `thingDef`、`count` | Def 必须存在、1–10 | 整阶段作废 |
| `pawn.spawn` | `pawnKind`、`count` | Def 必须存在、1–3 | 整阶段作废 |

**校验是全量的**：阶段里只要有一条不合法，整个阶段一条都不执行（不会留下半截副作用）。

## 4. 硬约束（都落在代码里）

| 约束 | 实现 |
|---|---|
| 脚本大小 | ≤ 64KB（`LuaStageRunner.MaxSourceBytes`） |
| 执行预算 | 墙钟 40ms、每片 4000 指令；超了判失败，不半途生效 |
| 动作数量 | 单阶段 ≤ 32 条 |
| 幂等 | `eventInstanceId + opId` 只成功执行一次，`executedOps` 随存档保存（上限 64） |
| 并发剧情 | 同时活跃 ≤ 6 条 |
| 存活期 | 5 游戏日无推进自动回收 |
| 阶段隔离 | 每次校验、预演与正式执行都在新的 Lua VM 中编译。用 `next_state` 把数据传给下一阶段 |
| 存档 | 保存脚本源码与实例状态。读档后执行阶段时重新编译 |

## 4.5 模型怎么知道脚本会做什么（0.4.1 补强）

这是本次最关键的可靠性问题：**模型不能只是"会写 Lua"，它必须知道每个动作在游戏里到底干什么。** 现在用四层机制保证：

### ① 动作手册由注册表生成，不是手写

每个 handler 在自己的类里声明规格：

```csharp
public string Describe() =>
    "story.show_choices{prompt=字符串≤600, options={{id,label}...}} —— 弹 2~4 个选项；" +
    "玩家点选后，脚本会在 trigger=\"choice_selected\" 被再次调用，选中项在 ctx.payload.choice 里";
```

`ActionRegistry.BuildManual()` 把它们拼成提示词里的动作手册。**手册与校验器是同一份代码**——改参数时忘记同步手册这件事从机制上不可能发生（以前是两份独立文本）。

### ② 合法 Def 名单，运行时现取

模型最容易犯的错是编 `ThingDef` / `PawnKindDef` 名字，然后整段被拒。现在提示词里直接给名单：

- `incident.fire`：来自候选表（已经过 `CanFireNow` 过滤，此刻真能触发）；
- `thing.spawn`：从 `DefDatabase<ThingDef>` 现取 14 个合法物品；
- `pawn.spawn`：从 `DefDatabase<PawnKindDef>` 现取 8 个 Humanlike 角色。

名单是运行时取的，不会像硬编码清单那样随版本过期。

### ③ 静态体检（LuaLint）：编译通过 ≠ 语义正确

执行前先查 5 类结构性错误，任何一条都直接拒：

| 检查 | 抓的问题 |
|---|---|
| 有没有 `function run(ctx, state)` | 最常见的手误 |
| 有没有 `rim.aist.json_encode` | 返回不了动作，等于没写 |
| `type = "..."` 是否都在注册表里 | 编造不存在的动作 |
| 用了 `show_choices` 是否处理 `choice_selected` | 玩家选完剧情卡死 |
| 注册了 timer 是否有对应分支 | 定时器永远不落地 |
| 是否既没 `done` 也没 `timer` | 事件挂 5 天后被回收 |

再加一条沙箱检查：出现 `require` / `io.` / `os.` / `coroutine` / `debug.` 直接拒。

### ④ 被拒了要把原因告诉模型

以前校验失败就丢弃，模型永远学不到。现在：**拒绝原因 + 上一版脚本回喂给模型，允许修一次**（只一次，避免无限烧 token）。提示词里会多出：

```
【上一版被拒绝了】
原因：story.show_choices{prompt=...} 校验失败：至少需要 2 个选项
上一版脚本：```lua ... ```
请按上面的约束修正后，重新输出完整脚本。
```

### 仍然存在的边界（不掩饰）

模型现在知道**契约**（参数、范围、触发时机、合法名字），但不知道**数值后果**——比如「在这个财富水平下 1.0 倍的 RaidEnemy 会有多强」。这靠 `points_multiplier` 与候选表类别粗粒度传递，真正的"后果感知"要等 P4 拿到历史战果统计后回喂给它。

## 4.6 延迟与阻塞（0.4.3 重做）

编剧那一趟可能写很久（几 KB 脚本 + 上千 token），所以必须说清楚**什么会被卡、什么不会**。

### 不会被卡住的

| 系统 | 为什么 |
|---|---|
| 原版事件（疾病、商队、访客、任务、轨道商船） | 走各自的 `StorytellerComp`，与本模组无关 |
| 叙述者 comp 的待发事件 | `MakeIntervalIncidents` 只看 `NarratorState.pending`，与网络无关 |
| **Lua 事件运行时** | `EventRuntime.Tick()` 由 `WorldComponentTick` 单独驱动，定时器与选项回调照常推进 |
| 其他模组的事件 | 我们没有 patch 叙述者，只有一条只读的 `IncidentWorker.TryExecute` Postfix |

### 之前会被卡住的（已修）

旧实现用**单一 `_inFlight`** 当闸门：编剧写作期间 `DirectorLoop.Tick()` 直接 return，
**下一次导演决策被堵住**。加上 600 秒默认超时与一次修复重试，最坏情况 AI 会有 **20 分钟不产生新事件**。

现在拆成两个独立槽位：

| 槽位 | 门控 | 说明 |
|---|---|---|
| 导演 | `_directorInFlight` | 同一时刻只允许一个导演请求 |
| 编剧 | `_writerInFlight` | 与导演**互不阻塞**；导演在编剧写作期间照常决策 |

导演若在编剧忙时又决定写剧情，只把概念**排队（最多 1 个，新的覆盖旧的）**，编剧槽位空出来立刻接上，不会开无限条线。

### 另外两个修正

- **编剧独立超时 `writerTimeoutSeconds`（默认 180 秒，可调 30–900）**：脚本就几 KB，没必要沿用导演的 10 分钟。
- **读档保护**：请求与排队概念绑定发起时的世界。加载存档后，旧世界的回复不会进入当前世界。

调试窗会显示「导演在途 / 编剧在途 / 排队概念」，能直接看出当前卡在哪。

## 4.7 "事件开了但毫无效果"的排查（0.4.5）

真机出现过一次：Lua 事件显示已开启，但屏幕上什么也没发生。逐条排查后定位到一个**静默失败**路径：

### 根因：空阶段被当成成功

`run()` 返回 `{ actions = {} }`（或 `{ actions = {}, done = true }`）时，
旧代码解析出 0 条动作、0 个定时器，然后"成功"地什么也没做，事件随即结束。
模型最常造成这种情况的写法是：

- `ctx.trigger` 判断写错（比如 `"on_start"`、`"begin"`），`start` 分支没命中；
- `actions` 用了字符串键（`actions["a"] = {...}`），json_encode 出来不是数组，解析器按数组读 → 0 条；
- 把 `done = true` 写在开头，什么都没做就收尾。

### 四条修正

| 修正 | 效果 |
|---|---|
| **空阶段直接判失败** | 动作 0 且定时器 0 → 报错 `空阶段：trigger="start" 阶段是空的…`，并触发一次模型修复 |
| **Lint 要求处理 `"start"`** | 脚本没有 `ctx.trigger` 或没有 `"start"` 分支，注册阶段就拒 |
| **Lint 查重复 opId** | 多个动作共用同一个 opId 会被幂等挡住，只执行第一条——这个错很难察觉，现在注册时直接拒 |
| **诊断可见** | 调试窗新增「最近阶段」（动作数/定时器数/done/stage）与「活跃事件」（阶段、定时器、错误），Player.log 里也有 `empty stage for evt_x: …` |

### 复现时的排查顺序

1. 打开调试窗看「最近阶段」：`动作 0` 就是空阶段；
2. 看「活跃事件」里的 `错误：` 字段；
3. `Player.log` 搜 `[AI Narrator]`，关键几行：
   - `empty stage for …` → 脚本没命中触发分支
   - `action … failed` → 动作执行抛异常
   - `lua rejected: …` → 体检/编译没过（原因会写清楚）

### 5.0 两种强制触发（调试窗，0.4.6）

调试窗顶部现在有两排控件，用来把 Lua 链路单独拎出来测：

| 按钮 | 会不会调模型 | 用途 |
|---|---|---|
| **立即请求一次** | 会（导演） | 走完整链路：导演决定 → 可能选原版事件/休整/写剧情 |
| **强制写 Lua 剧情** | 会（只调编剧，跳过导演） | 下面输入框里的概念直接交给编剧，不用等 MTB、也不受导演选什么影响 |
| **注入示例事件** | **不会** | 直接把内置示例脚本注册并启动，验证 Lua 运行时/动作层/定时器 |

排查逻辑：

- 「注入示例事件」能出信 + 选项 → **运行时是好的**，问题在"模型写的脚本"或请求链路；
- 「注入示例事件」也没反应 → 查看调试窗「最近阶段」及启动日志，确认 RimLua 已初始化、C# 动作已注册。
- 「强制写 Lua 剧情」失败但示例能跑 → 看调试窗「最近阶段」与日志里的 `script rejected` / `empty stage`。

## 4.8 短线 / 长线事件开关（0.4.7）

Lua 事件不一定是长线。**默认只生成短线事件**，长线要玩家明确打开。

| 设置 | 默认 | 行为 |
|---|---|---|
| 允许长线事件（多阶段 / 跨天定时器） | **关** | 关：编剧被要求不用 `timer`，一到两次交互内收尾；开：允许用 `timer` 推进后续阶段 |

选项旁边的说明原文：

> 关闭时只生成当场结束的短线事件。建议保持关闭：AI 写的长线事件经常前后不连贯、伏笔收不回来，
> 玩家体验往往很差；短线事件（一封信、一次抉择、一个后果）反而更稳。需要长线时再打开。

**硬兜底**：玩家关闭时，脚本里只要注册了 `timer` 就直接拒（并触发一次修复重写），
不会出现"设置关了但 AI 还是写长线"的情况。

### 短线事件的两种合法形状

```lua
-- A. 不用选项：一个阶段内讲完
if ctx.trigger == "start" then
  actions[1] = { opId="a1", type="story.send_letter", args={title="…", text="…"} }
  actions[2] = { opId="a2", type="incident.fire", args={defName="…", points_multiplier=1.0} }
  return rim.aist.json_encode({ actions = actions, next_state = s, done = true })
end
```

```lua
-- B. 一次抉择：start 等待，choice_selected 收尾
if ctx.trigger == "start" then
  -- show_choices
  return rim.aist.json_encode({ actions = actions, next_state = s })
elseif ctx.trigger == "choice_selected" then
  -- 按选择给出后果
  return rim.aist.json_encode({ actions = actions, next_state = s, done = true })
end
```

另外新增"**悬空事件**"检查：一个阶段既不 `done`、也没有 `timer`、也没有等待玩家选择 → 直接拒，
因为这种事件只会挂到 5 天后被回收，玩家什么也看不到。

## 4.9 脚本输出格式改了（0.4.7）

之前要求模型返回 `{"title":"...","lua":"..."}` —— **这是格式失败的主因**：
把整段 Lua 塞进 JSON 字符串需要正确转义换行与引号，模型经常写出裸换行，整份回复就不可解析。

现在改成**代码块优先**：模型第一行写 `TITLE: 标题`，紧跟一个 `lua` 标记的围栏代码块，
块内是完整脚本（不再需要任何 JSON 转义）。

- 解析器先找 ```lua 代码块（标题从代码块前的 `TITLE:` / `标题：` 行取）；
- 找不到代码块才回退到 JSON（兼容旧模型习惯）；
- 两条路都失败才报错，错误信息会说明"既没有代码块也没有 JSON"。

这样"脚本内容对不对"和"回复格式对不对"就解耦了——格式问题不再让整份脚本作废。
