# 动作库扩展计划 v2（P4）

> 一句话：不是"再加十个动作"，而是先把动作**指得准、看得见、算得清**，再往"人心 / 现场 / 交互"三层扩。
> **已实施：0.6.0，动作 26 → 42（B0 + B1 + B2 + B3，B4 未做）**。交付细节见 [P4-交付说明](P4-交付说明.md)。

- 现状版本：0.6.0，`ActionRegistry.RegisterBuiltins()` 注册 **42 个**动作
- 本文性质：**计划案 + 实施记录**。所有"人日"是粗估，不是承诺
- 实施偏差（3 处，均因 1.7 API 变化或按你的要求）：
  1. `pick_cell` / `pick_pawn` 不做（你明确排除）；
  2. `story.focus` 只有镜头，没有音效——1.7 的 `SoundDef` / `SoundRoot` / `SoundStarter` 都没有公开播放入口；
  3. `story.objective` 用"信件 + 每日消息"代替常驻 Alert——`AlertsReadout` 没有公开注册入口。
- 与 P3 的关系：P3 的 B1–B4 已落地（`world.site` 除外）；但 P3 里标"必做"的 **I0 只做了一半**——预算池有了（3 个），
  "动作分组 / 按形态裁剪"没进代码，手册仍是全量注入。本计划把 I0 补齐，再往下扩。

## 0. 现状盘点

### 0.1 26 个动作的分布

| 层 | 数量 | 动作 |
|---|---|---|
| 叙事 | 6 | send_letter、show_choices、dialog、message、remember、highlight |
| 生成 | 4 | thing.spawn、pawn.spawn、story.reward、map.drop_pod |
| 地图 | 5 | weather、condition、plant、fire、damage |
| 角色 | 8 | hurt、heal、gear、set_skill、kill、join、map.corpse、incident.fire |
| 世界 | 3 | faction.goodwill、research.grant、quest.start |

看得出问题：**"东西"很足，"人"和"现场"是空的。** 现在能造事故，造不出反应；
能扔一具尸体，造不出"谁为他难过"。

### 0.2 四处结构性缺口（都有代码依据）

| # | 缺口 | 证据 | 后果 |
|---|---|---|---|
| 1 | **坐标靠猜** | 5 个动作只吃绝对 `{x,y,z}`（fire / damage / corpse / plant / highlight），校验只有 `cell.InBounds`（MapHandlers.cs:124、StoryHandlers.cs:96）；`ctx` 不含地图宽高与中心（EventRuntime.cs:390-398），写手提示词里也没有 | 模型不知道地图多大，越界即**整段作废** |
| 2 | **目标只能指向"本次生成物"** | `pawn.*` 只认 `handle`（PawnHandlers.cs:59）；`HandleRegistry.Register` 只在 thing.spawn / pawn.spawn / map.corpse 里调用 | 无法对**已存在的殖民者**做任何事；"你的射手受伤了"写不出来 |
| 3 | **执行结果不回灌** | `ctx` 只有 trigger / payload / instance_id / event_title / day / colonists / stage；执行完只写 `instance.lastError` 给 UI | 多阶段脚本无法判断上一阶段成不成，只能盲写 |
| 4 | **提示词是全量的** | 手册 26 行 **2101 字**（实测），13 行 Def 名单约 **1.9k 字**，WriterCore 737 + WriterRules 733 → 单次约 **7.6k 字**；`BuildManual()` 与 `BuildDefSection()` 都是无条件拼接（PromptBuilder.cs:175、212） | 26 → 39 个动作会推到 10k 字；模型选错动作的概率随手册长度上升 |

> 第 4 条是这份计划把 B0 放在第一位的原因：**动作库可以大，单次可见的动作必须小。**

### 0.3 现在的失败模式已经变了

P2/P3 时的问题是"能力不够"；现在调试窗里最常见的拒绝原因是三类：
空阶段（trigger 名字对不上）、悬空事件（没 done 没 timer）、坐标/Def 非法。
这三类都是**可靠性**问题，加动作只会放大它们。所以顺序是：先修地基，再加楼层。

## 1. 设计约束（P3 三条 + 新增两条）

1. 每个动作都要在 prompt 里占一行 → **必须能裁剪**，单次可见 ≤ 20 个。
2. 带 Def 名字的动作必须同时给合法名单 → **名单按需注入**，不再 13 行全带。
3. 每个动作都要有预算（数量、范围、冷却）→ 新增 **World / Social** 两个池。
4. **目标必须可解析**：新增动作一律用 `who` / `spot` 语义，禁止让模型自由发挥坐标与对象。
5. **危险动作只能指向 AI 自己生成的对象**：玩家殖民者只接受"正向动作"（见 §9 矩阵）。

## 3. B0 地基（3 人日，5 项）

| 项 | 内容 | 为什么必须 |
|---|---|---|
| B0-1 **锚点定位** | 新 `ActionSpot`：`spot="colony_center" / "storage" / "water" / "ore" / "edge_north" / "handle:p1"` + `offset={x,y}`，与 `cell` 二选一；`ctx` 增 `map_w / map_h / center` | 消掉"猜坐标 → 越界 → 整段作废"这条最高频的失败链 |
| B0-2 **分层手册** | `IGameActionHandler.Category`（narrative / spawn / map / pawn / social / world）；`BuildManual(categories)`；`BuildDefSection(categories)` 只注入相关名单 | 动作涨到 39 个时，单次输入仍能压到 ≤ 7k 字（见 §8） |
| B0-3 **目标选择器** | 新 `WhoResolver`：`who="handle:p1" / "colonist:米娅" / "best:Shooting" / "worst:Mood"`；解析失败 → 该动作校验失败（保持整段作废） | 让剧情能落到"具体的人"身上，而不是每次都凭空生一个 |
| B0-4 **执行回执** | `ctx.last` = 上一阶段的 `[{type, ok, error}]`（≤8 条），由 EventRuntime 填 | 多阶段脚本第一次能"知道自己刚才成没成" |
| B0-5 **预算统一** | 池扩为 Spawn 40 / Danger 3 / PawnEdit 8 / **Social 6** / **World 2**；每个动作在 `Describe()` 里声明所属池 | 没有池的动作等于给模型无限子弹 |

**验收**：B0 落地后，现有 26 个动作的 mock 全链路（`mock:story`）行为不变；
`LastPlanSummary` 与动作数逐条一致。这是后面所有批次的前置门槛。

> 风险提示：B0 横跨 EventRuntime / ActionRegistry / PromptBuilder 三个核心文件，
> 是这份计划里唯一"改坏了会静默影响已有动作"的部分。它必须单独交付、单独回归。

## 4. B1 心理与关系（6 个，3.5 人日）

这一批解决"事件发生后，没有人有反应"。

| opType | 参数与上限 | 池 | API | 置信度 | 用它讲什么 |
|---|---|---|---|---|---|
| `pawn.thought` | who、thoughtDef、days 1~15、other? | Social（≤6/事件） | `MemoryThoughtHandler.TryGainMemory` | 高 | 让殖民者对事件有情绪记忆（"他记得那天"） |
| `pawn.mood` | who、delta −0.15~0.15 | Social（1 次） | `Need_Mood.CurLevel` | 高 | 小幅情绪推动，不替代想法系统 |
| `pawn.inspiration` | who、inspirationDef | Social | `InspirationHandler.TryStartInspiration` | 中高 | 危机后灵感（"他整夜没睡，然后想通了"） |
| `pawn.trait` | who、traitDef、remove? | PawnEdit | `TraitSet.GainTrait / RemoveTrait` | 高 | 创伤改变一个人；只对 AI 生成 NPC |
| `pawn.relation` | who、other、relationDef | Social | `Pawn_RelationsTracker.AddDirectRelation` | 中 | 建立敌友/亲属（双向），只对 AI 生成 NPC |
| `pawn.mental` | who、mentalStateDef | Danger（1 次） | `MentalStateHandler.TryStartMentalState` | 中高 | 崩溃（daze/berserk）；**只对 AI 生成 NPC**，P2 |

**为什么"想法"优先于"心情"**：`pawn.mood` 直接改数值，最省事也最廉价，滥用会让玩家觉得"心情是假的"；
`Thought_Memory` 走原版心情计算，会进入玩家的"想法清单"，可解释、可追溯。所以 mood 只留 ±0.15 的微调位。

## 5. B2 场景与破坏（7 个，3 人日）

这一批解决"事件现场看起来和昨天一模一样"。

| opType | 参数与上限 | 池 | API | 置信度 | 用它讲什么 |
|---|---|---|---|---|---|
| `map.building` | thingDef（建筑）、spot、stuff? | Spawn（≤8） | `ThingMaker.MakeThing` + `GenSpawn.Spawn` | 中 | 废墟墙体、路障、临时哨站 |
| `map.terrain` | terrainDef、spot、radius 0~4 | Spawn | `TerrainGrid.SetTerrain` | 高 | 焦土、泥泞、被踩出来的路 |
| `map.roof` | roofDef、spot、radius 0~4 | Spawn | `RoofGrid.SetRoof` | 高 | 塌陷的坑道、洞穴入口 |
| `map.filth` | filthDef、spot、count 1~8 | Spawn | `FilthMaker.TryMakeFilth` | 高 | 血迹、灰烬、碎屑 —— **最便宜的氛围** |
| `map.animal` | pawnKind（动物）、count 1~6、spot、manhunter? | Spawn（≤6） | `PawnGenerator` + `GenSpawn` | 高 | 兽群、虫害、迁徙 |
| `map.remove` | spot、radius 1~3、only=plants/filth/debris/ai_buildings | Danger | `Thing.Destroy` | 中 | 清出空地、烧掉残骸；**只删 AI 生成的与非结构物** |
| `map.collapse` | spot、radius 1~2 | Danger | 屋顶移除 + `GenExplosion`（塌方伤害） | 中 | 矿难、地道塌方 |

> `map.remove` 是这一批唯一的风险点：删错东西不可撤销。默认只允许删三类——植物、污渍、本事件句柄指向的物体。

## 6. B3 交互与呈现（5 个，3.5 人日）

这一批解决"玩家只能读文字、点选项"。

| opType | 参数与上限 | 池 | API | 置信度 | 用它讲什么 |
|---|---|---|---|---|---|
| `story.pick_cell` | prompt≤120、mustBeWalkable? | — | `Targeter.BeginTargeting` → 回调回填 `payload.cell` | 中 | 让玩家**在地图上点**"去哪儿调查"；选中格直接给后续阶段用 |
| `story.pick_pawn` | prompt≤120、filter=colonist/any | — | 自绘列表（复用现有弹窗）或原版 ChoosePawn | 中 | 让玩家选"派谁去"；选中者自动登记为句柄 `chosen` |
| `story.objective` | text≤120、days 1~10 | — | `Alert` + `AlertsReadout` 注册（或复用 letter） | 中高 | 给长线事件一个"还剩几天"的常驻目标 |
| `story.focus` | spot、soundDef?、letterDef? | — | `CameraJumper.TryJump` + `SoundStarter.PlayOneShot` | 高 | 镜头与音效，零叙事风险的"演出" |
| `story.choice_letter` | 同 show_choices，但走原版 `ChoiceLetter` | — | `LetterMaker` + `Find.LetterStack` | 中低 | P2 遗留项：选项进信件栏，不弹窗打断 |

**风险**：`pick_cell` / `pick_pawn` 会**暂停玩家的操作**，中途取消、存档、读档都要处理干净；
这是整个计划里最容易出 bug 的两个动作，建议放到 B3 最后做，且默认关闭、由玩家在设置里开。

## 7. B4 世界层（3 个，4 人日）

| opType | 参数与上限 | 池 | API | 置信度 | 用它讲什么 |
|---|---|---|---|---|---|
| `world.site` | sitePartDef、tile?、factionDef?（1 处/天） | World | `SiteMaker.MakeSite` + `Find.WorldObjects.Add` | 中 | 世界上多一个可探索地点（P3 唯一没落地的） |
| `faction.hostility` | factionDef、hostile | World | `Faction.SetRelationDirect` | 中高 | 宣战/停战（重大，需二次确认） |
| `world.caravan` | factionDef、goods? | World | `CaravanMaker.MakeCaravan` | 中低 | 商队来访/离开，把叙事推到地图之外 |

**为什么建议缓**：世界层的错误不会当场暴露，要玩家出地图才发现；调试成本是地图内的 3 倍以上。
且 `world.site` 进去以后仍走原版 GenStep，叙事收益没有想象中大。

## 8. 提示词预算（这是全篇最硬的约束）

| 项 | 现在（26 个） | +13 个（不裁剪） | +13 个（B0-2 裁剪后） |
|---|---|---|---|
| 动作手册 | 2101 字 | 约 3160 字（39 × 81 字） | 约 1620 字（单次只显示 20 个） |
| Def 名单 | 约 1900 字（13 行全带） | 约 3300 字（25 行） | 约 1000 字（只带本次用到的 6 行） |
| WriterCore + Rules | 1470 字 | 1470 字 | 1470 字 |
| 用户段（概念 / 候选 / 快照 / 说明） | 约 2100 字 | 约 2100 字 | 约 2100 字 |
| **单次合计（约）** | **7.6k 字** | **10.0k 字（+32%）** | **6.2k 字（−18%）** |

结论两条：

1. **不做 B0-2 就加动作，提示词涨 32%**，且涨的全是"这次用不上"的动作 —— 这是模型选错动作的直接来源。
2. **做了 B0-2 反而更短**：加了 13 个动作，单次输入反而从 7.6k 降到 6.2k。
   所以"动作库可以大"不是乐观估计，是裁剪换来的。反过来说，B0-2 没做完之前，不应该加超过 5 个动作。

## 9. 安全边界：动作 × 目标

`who` 解析出对象之后，还要过一道**目标类型**检查。默认矩阵：

| 动作类别 | AI 生成 NPC | 玩家殖民者 | 玩家建筑/物品 |
|---|---|---|---|
| 正向（heal、inspiration、正面 thought、story.focus） | 允许 | **允许** | 允许（仅生成类） |
| 中性（thought 负面、gear、set_skill、objective、filth） | 允许 | **默认禁止**，可在设置里开 | 禁止 |
| 危险（kill、hurt、mental、join、trait、relation、remove、damage） | 允许（受危险预算） | **一律禁止** | 仅本事件生成物 |

这道检查必须写在 **C# 的 Validate 里**，不能只写在提示词里。提示词是建议，Validate 才是墙。

## 10. 明确不做

| 不做 | 原因 |
|---|---|
| 改玩家殖民者的身份/意识形态/工作分配 | P3 红线，继续保留（心理层的"正向动作"是唯一例外，见 §9） |
| 自由几何的地图生成（SceneBlueprint） | 需要 GenStep + 蓝图编译器，是另一个项目 |
| 自定义任务系统（QuestPart 组合） | 原版 QuestPart 有 300+ 子类，接进来等于重写任务系统；先用 `story.objective` 过渡 |
| 让模型直接生成 Def / DefName | 名单之外的 Def 一律拒，继续走 ActionCatalog |
| 动作执行异步化 / 跨 tick 动画 | RimWorld 主线程模型下收益低、风险高 |

## 11. 验收标准（每批都要过）

| # | 标准 |
|---|---|
| 1 | 每个动作都有 `Describe()` / `Validate()` / `Execute()`，且 `Validate` 无副作用 |
| 2 | 每个动作至少 1 条**负例**（非法 Def、越界、超预算）在离线测试里被拒，且是整段作废 |
| 3 | 每个动作都有 demo 脚本；`mock:story` 扩成 3 段，覆盖全部新增动作 |
| 4 | 单次写手输入 ≤ 7000 字（含 system + user），且不高于本批实施前的实测值；超了就先裁剪，不加动作 |
| 5 | 新增动作不改变 26 个旧动作的行为（旧脚本跑出的 `LastPlanSummary` 逐字一致） |
| 6 | 调试窗能看到每个动作的"类型 / 结果 / 失败原因" |
| 7 | 预算池不可绕过：每个新动作在 `Describe()` 里声明池，且 Validate 里 check、Execute 里扣 |

## 12. 三条路径

| 档 | 内容 | 人日 | 动作数 | 适合 |
|---|---|---|---|---|
| **最小** | B0 + B1 | 6.5 | 32 | 只想让"人"活起来 |
| **推荐** | B0 + B1 + B2 | **9.5** | **39** | 人心 + 现场都有了，风险可控 |
| **全做** | B0–B4 | 17 | 47 | 一次到位，但 B3/B4 需要真机反复验证 |

我的建议是**推荐档**，并且拆成三次交付：

1. **B0 单独交付**（3 人日）—— 不动任何叙事行为，只让地基更稳；
2. **B1 交付后先玩一周**（3.5 人日）—— 确认"想法/心情"的力度合适，再决定危险动作要不要开；
3. **B2 最后做**（3 人日）—— 纯表现层，随时可以砍。

如果你只想要一个动作：**`map.filth`**（半天，最便宜的氛围）或 **`pawn.thought`**（1 天，最直接的"有人反应"）。

## 附：每新增一个动作的固定成本

| 触点 | 工作量 |
|---|---|
| Handler 三件套（Describe / Validate / Execute） | 60~120 行 |
| 注册 + 分类 + 预算池声明 | 5 行 |
| ActionCatalog 名单（若带 Def） | 10~20 行 |
| 文档（动作库参考 / 编剧提示词） | 各 1 行 ~ 1 段 |
| demo 脚本 + mock 覆盖 | 0.2 人日 |
| 提示词预算复核 | 0.1 人日 |

简单动作约 **0.4 人日/个**；带新子系统（Alert、Targeter、世界对象）另加 0.5~1 人日。
上面各批的人日已含这部分，不是额外叠加。
