## 1. 这一版能干什么

以前：叙述者占位，什么都不发。
现在：**AI 能自主决定「休整」还是「发一次原版事件」，并且发出来的事件一定在候选表内、不重复、不超配额。**

一次完整链路：

```
WorldComponentTick（主线程）
  └─ 每 60 tick 才判断一次（MTB 按 60 tick 换算，逐 tick 会放大 60 倍）
       ├─ 闸门：已配置 / 自动触发开 / 无在途 / 今日未超额 / 未在失败退避 / 过了最小间隔
       ├─ Rand.MTBEventOccurs(aiMtbDays)
       └─ Dispatch：建快照 → 过滤候选 → 拼 prompt → 后台 HTTP → 回调进队列
                                                            │
DrainInbox（主线程）────────────────────────────────────────┘
       ├─ 过期检查（真实时间，超过超时 + 15 秒）→ 丢弃
       ├─ 解析 JSON（去围栏 / 补截断 / 括号配平）
       ├─ no_event → 张力衰减，写日志
       └─ vanilla_incident → 白名单校验 → 配额校验 → 入 pending（600~2500 tick 后发）
                                                            │
MakeIntervalIncidents（主线程，惰性迭代器）─────────────────┘
       └─ 到点 → 重建 IncidentParms → **CanFireNow 复检** → yield 一条 FiringIncident
```

> **候选表的两道门（0.3.3 修的 bug）**：早期版本只在启动时按类别扫了一遍，
> 于是模型会挑到"当前根本不满足触发条件"的事件（研究没解锁、需要特定派系、
> 已有同类事件在冷却），选中后静默失败。现在：
> 1. 每次请求前用 `IncidentDef.TargetAllowed(map)` + `IncidentWorker.CanFireNow(parms)` 现算候选；
> 2. 批准到发射之间还要再复检一次，条件变了就作废并记 `fired=false`（不占配额）。

把设置页的「接口地址」填成 `mock:xxx`，模型名和 Key 随便填非空字符串即可（用于通过"已配置"检查）。然后打开调试窗点「立即请求一次」。

| 地址 | 期望结果 |

| `mock:raid` | 批准一个 Threat 事件，状态「已批准：XXX（N tick 后发射）」，几秒内真实触发 |
| `mock:garbage` | 状态「提案非法：no json object in response」 |
| `mock:hallucinate` | 状态「拒绝：候选表里没有 RaidEnemyFromTheFuture」——白名单生效 |

## 5. 已知取舍

- **不重试模型返回的非法 JSON**：一次失败即记 failStreak，等退避后再来。理由：省 token，且非法输出通常是配置或模型能力问题，重试收益低。
- **`mock:` 前缀是正式功能**，不是临时 hack——它让"没有 Key 的玩家 / CI"也能验证链路，后续 P2 也会复用。
- **pending 只保留 1 条**：一次只发一个事件，避免同一时刻炸出多个剧情。
- **状态整包 JSON ≤ 200 条历史**，超出丢最旧。

## 7. 设置页自查（0.3.5 / 布局规则 0.4.4）

### 7.0 布局规则（踩过两次坑之后定下的）

| 规则 | 原因 |
|---|---|
| **控件高度恒定**：任何"勾选后才出现"的控件都改成常驻 + 灰掉 | 勾选会在一帧内改变内容高度，而滚动视口高度来自上一帧测量 → 内容被裁、滑条消失 |
| **关键动作放固定底栏**，不参与滚动 | 即使高度算错，按钮也点得到 |
| **滚动视口只增不减** | 测量异常时宁可滚动条长一点，也不能把已经够用的视口缩小 |
| **测量只作修正**，初值给足（1600） | 首帧没有测量值 |

按这四条，0.4.4 把两处动态重排都消掉了：
「完全覆盖系统提示词」的文本框现在常驻（未启用时灰掉），
「模型选择」按钮在没有预置列表的服务商下也常驻（灰掉并提示手填）。

### 7.1 上一版为什么"更严重"

0.3.4 我改成"读上一帧内容高度自适应"，但读的位置错了：

```csharp
float used = listing.CurHeight;   // ← 在 End() 之前读
listing.End();
_contentHeight = used + 28f;
```

`Listing_Standard.CurHeight` 要到 `End()` 之后才可靠。首帧读到 0，于是 `_contentHeight = 28`；
而下一帧 `Mathf.Max(28, inRect.height)` 又把它抬回"对话框高度"，
结果是**滚动范围正好为 0**——比 0.3.3 的固定 1160 更糟：1160 至少还能往下滚 400 多像素，
28 是彻底滚不动，页面下半截永远看不到。

修正（照 RimLua 设置页的写法，同版本已跑通）：

```csharp
listing.End();
float measured = listing.CurHeight;   // ← End() 之后读
if (measured > 100f) _contentHeight = measured + 16f;
Widgets.EndScrollView();
```

外加两道保险：`_contentHeight` 初值给 1600（宁可滚动条长一点）；只有测到 >100 的合理值才更新。

### 7.2 结构改成「滚动区 + 固定底栏」

关键按钮不再放在滚动内容里：底栏固定显示「恢复默认参数 / 调试窗口 / 保存设置」，
无论滚动在哪、无论内容高度算得对不对，都点得到。

### 7.3 顺带修掉一个更严重的运行时隐患

`0.3.3` 加的"发射前 `CanFireNow` 复检"没有异常保护：

```
MakeIntervalIncidents (迭代器)
  └─ candidate.Def.Worker.CanFireNow(parms)   ← 若 worker 抛异常
       → 异常穿透叙述者 tick
       → state.pending.RemoveAt(0) 永远执行不到
       → 该 pending 每 tick 重试一次，每 tick 刷一条红字
```

现在改成：**先出队，再算**；`DefaultParmsNow` / `CanFireNow` 全程 try/catch；
失败只记一条 `fired=false` 历史并 `yield break`，绝不抛给叙述者。
（C# 限制：`yield return` 不能写在带 catch 的 try 里，所以先算出 `FiringIncident` 再 yield。）

同时把候选表里逐个 def 的告警压成一条汇总日志：
`candidates: 37 firable / 212 total (175 rejected by CanFireNow, last error NullReferenceException)`。
