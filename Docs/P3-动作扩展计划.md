# Lua 动作库扩展计划 v0.1

- 现状：**6 个动作**（send_letter / show_choices / remember / incident.fire / thing.spawn / pawn.spawn）
- 目标：让 AI 能在"叙事—地图—角色—任务"四个层面表达，而不是只能发信 + 生东西
- 文档性质：**v0.5.0 已按"全做"实施**。除 `world.site` 外全部落地（原因见文末）。

---

## 0. 先说三条设计约束（决定这份表怎么排）

1. **每个动作都要在 prompt 里占一行**。动作从 6 涨到 25，system prompt 会多出约 1200 token。
   → 必须做「按形态裁剪」：短线事件不注入 timer/site 相关动作，只给当前用得上的子集。
2. **凡是带 Def 名字的动作，必须同时给合法名单**。否则模型一定编名字，然后整段被拒
   （`thing.spawn` / `pawn.spawn` 就是这么做的）。
3. **每个动作都要有预算**：数量、范围、冷却。没有预算的动作等于给模型一把无限子弹的枪。

## 1. 批次划分总表

| 批次 | 主题 | 动作数 | 人日 | 风险 | 建议 |
|---|---|---|---|---|---|
| **B1** | 叙事与提示 | 4 | 1.5 | 低 | **强烈建议先做** |
| **B2** | 地图与氛围 | 7 | 3 | 中 | **建议做** |
| **B3** | 角色（Pawn） | 6 | 3.5 | **高** | 可延后 |
| **B4** | 任务 / 派系 / 研究 | 4 | 2.5 | 中高 | 可延后 |
| **I0** | 支撑设施（提示裁剪、预算池、名单注入） | — | 2 | 低 | **必做，B1 的前置** |

合计 **12.5 人日**。但可以只做 `I0 + B1 + B2` = **6.5 人日**，就能覆盖 80% 的叙事需求。

## 2. B1 叙事与提示（4 个，1.5 人日）

| opType | 参数 | 上限 | 权限 | 映射 API | 置信度 | 用途 |
|---|---|---|---|---|---|---|
| `story.message` | `text`、`kind`(neutral/positive/negative) | text ≤ 200 | P0 | `Messages.Message(text, MessageTypeDef, false)` | **高**（已在用） | 屏幕顶部小提示，不打断、不进信件栏 |
| `story.dialog` | `title`、`text` | text ≤ 1500 | P0 | 复用现有 `Dialog_NarrativeChoice`（无选项版） | **高**（自有 UI） | 纯叙事弹窗，适合"一次性的氛围描写" |
| `story.highlight` | `cell` 或 `thingId`、`duration` | 5 秒 | P0 | `TargetHighlighter.Highlight(...)` | 中 | 把玩家视线引到某个地点（"你在东边看到了什么"） |
| `story.reward` | `thingDef`、`count`、`quality` | count ≤ 5 | P1 | `ThingMaker.MakeThing` + `GenPlace.TryPlaceThing` | **高** | 剧情奖励（比 `thing.spawn` 语义清楚：直接放进仓库/地面指定点） |

> `story.reward` 与现有 `thing.spawn` 的差别：后者是"在基地附近随机落地"（叙事用），
> 前者是"给玩家一份明确奖励"（结算用），参数里带品质与指定落点。

## 3. B2 地图与氛围（7 个，3 人日）

| opType | 参数 | 上限 | 权限 | 映射 API | 置信度 | 用途 |
|---|---|---|---|---|---|---|
| `map.weather` | `weatherDef` | 持续 ≤ 1 天 | P1 | `map.weatherManager.TransitionTo(def)` | 中高 | 风暴/雾/雨，配合剧情气氛 |
| `map.condition` | `conditionDef`、`durationHours` | ≤ 48 小时 | P1 | `GameConditionMaker.MakeCondition` + `map.gameConditionManager.RegisterCondition` | 中高 | 日蚀、毒雾、寒潮、极光 |
| `map.fire` | `cell`、`size` | size ≤ 3 格 | P1 | `FireUtility.TryStartFireIn(cell, map, size)` | 高 | 起火（事故、纵火、战斗余烬） |
| `map.damage` | `cell`、`radius`(≤3)、`damageDef` | 1 次 | **P2** | `GenExplosion.DoExplosion(...)` | 中 | 爆炸/塌方，会伤到人 → 必须计入危险预算 |
| `map.drop_pod` | `thingDef`、`count`、`cell` | count ≤ 20 | P1 | `DropPodUtility.DropThingsNear(...)` | 中 | 空投物资/补给（叙事上很有画面感） |
| `map.corpse` | `pawnKind`、`cell`、`deathCause` | 1 具 | P1 | 生成 Pawn → `pawn.Kill(...)` → 自然产生 Corpse | 中高 | **叙事核心**：现场尸体 |
| `map.plant` | `plantDef`、`cell`、`growth` | 5 株 | P1 | `GenSpawn.Spawn(ThingMaker.MakeThing(plantDef))` | 中 | 植被异常（孢子树、枯萎） |

> `map.damage` 是我唯一标 P2 的：它会伤到玩家的人，必须走"危险预算 + 显式记录"，
> 而且要检查玩家 Pawn 是否在影响范围内。

## 4. B3 角色（6 个，3.5 人日，风险最高）

| opType | 参数 | 上限 | 权限 | 映射 API | 置信度 | 用途 |
|---|---|---|---|---|---|---|
| `pawn.hurt` | `pawnHandle`、`hediffDef`、`severity` | severity ≤ 0.8 | P1 | `HediffMaker.MakeHediff` + `health.AddHediff` | 高 | 受伤/中毒/感染 |
| `pawn.heal` | `pawnHandle`、`hediffDef?` | — | P1 | `health.RemoveHediff` / `health.RestorePart` | 中高 | 治疗、移除状态 |
| `pawn.kill` | `pawnHandle`、`cause` | 1 人 | **P2** | `pawn.Kill(DamageInfo?, Hediff?)` | 高 | 明确死亡（会真实产生尸体） |
| `pawn.gear` | `pawnHandle`、`thingDef`、`slot` | 1 件 | P1 | `pawn.apparel.Wear` / `equipment.AddEquipment` | 中 | 装备（给幸存者一件东西） |
| `pawn.set_skill` | `pawnHandle`、`skillDef`、`level` | 0–20，仅 AI 生成的 NPC | P1 | `pawn.skills.GetSkill(...).Level` | 高 | 让 NPC 真的"是个工程师" |
| `pawn.join` | `pawnHandle` | 1 人 | **P2** | `pawn.SetFaction(Faction.OfPlayer)` | 高 | 幸存者加入（重大，需玩家确认） |

**风险说明**：这批唯一的难点不是 API，而是**句柄**。Lua 里没有对象引用，
必须先建立"pawnHandle → Pawn"的解析层（生成时登记，读档时重建），否则动作无处落脚。
这也是 B3 比 B1/B2 贵一倍的原因。

**明确不做**：修改已有玩家殖民者的身份/意识形态/工作分配/派系——只对 AI 自己生成的 NPC 生效。

## 5. B4 任务 / 派系 / 研究（4 个，2.5 人日）

| opType | 参数 | 上限 | 权限 | 映射 API | 置信度 | 用途 |
|---|---|---|---|---|---|---|
| `quest.start` | `questScriptDef`、`points` | 1 个 | P2 | `QuestUtility.GenerateQuestAndMakeAvailable(...)` | 中 | 抛出原版任务（学术、援救、遗迹） |
| `faction.goodwill` | `factionDef`、`delta` | ±30 | P2 | `faction.TryAffectGoodwillWith(...)` | 中高 | 外交后果（"他们记住了你"） |
| `research.grant` | `researchDef`、`amount` | ≤ 项目 50% | P2 | `Find.ResearchManager.AddProgress(...)` | 中高 | 研究奖励（遗迹考察） |
| `world.site` | `sitePartDef`、`tile`、`factionDef` | 1 处 | P2 | `SiteMaker.MakeSite` + `Find.WorldObjects.Add` | 中 | 在世界地图上放一个可探索地点 |

> `world.site` 只是**建站点**，不含自定义地图生成——进入后仍走原版 GenStep。
> 真正的地图自由设计（SceneBlueprint）不在本计划内。

## 6. I0 支撑设施（2 人日，必做）

| 项 | 内容 | 为什么必须先做 |
|---|---|---|
| 动作分组与提示裁剪 | 给每个动作打 `category`（narrative/map/pawn/quest），按当前形态（短/长）与开关只注入相关子集 | 否则 25 个动作会把 system prompt 撑到 3000+ token，模型反而更容易出错 |
| Def 名单注册 | 每个带 Def 参数的动作声明"名单来源"（天气/状况/植物/状况/任务…），提示词自动附带 | 不给我名单 = 模型编名字 = 整段被拒 |
| 统一预算池 | `SpawnBudget`（生成物）、`DangerBudget`（伤害/爆炸）、`WorldEditBudget`（站点/派系） | 现在只有零散的上限，加动作前必须有统一口径 |
| 句柄层（B3 前置） | `HandleRegistry`：Lua 里只看到 `"p1"` 这种 id，C# 侧映射到真实 Pawn/Site，读档后重建 | 没有它就做不了任何"对已存在对象动手"的动作 |

## 7. 验收标准（每批都要过）

| # | 标准 |
|---|---|
| 1 | 每个新动作都有 `Describe()`（进 prompt）与 `Validate()`（纯校验，不产生副作用） |
| 2 | 非法参数（越界数量、不存在的 Def、超预算）→ 整阶段作废，**不留半截副作用** |
| 3 | 每个动作都有对应 demo 脚本，能在「注入示例事件」里跑通 |
| 4 | 新动作不改变原有 6 个动作的行为 |
| 5 | 动作总数 ≥ 20 时，短线事件的 system prompt 仍 ≤ 2500 token |

---

## 8. 我的建议

**先做 `I0 + B1 + B2`（6.5 人日）**，理由：

- B1 解决"叙事手段太单一"（只有信和选项，没有提示、没有高亮、没有明确奖励）；
- B2 解决"世界没有反应"（天气、疫情、火、空投、尸体）——这五个是玩家最能感知的"后果"；
- B3/B4 的 API 风险高、还需要句柄层，等 B2 用一段时间、确认动作层稳定后再做。

如果你只想要最小增量：**B1 的 4 个动作（1.5 人日）**，几乎零风险，立刻让叙事手段翻倍。
